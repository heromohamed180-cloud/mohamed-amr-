When the Right Dashboard
Leads to the Wrong Decision

A simulation of a real-world validation failure
caused by mismatched data granularity.

The Business Question

“

What happened during Q4 2024?

Did sales increase or decline?
Which categories and cities contributed the most,
and are there any noticeable changes that require attention?

”

This is one of the most common business questions a data analyst receives.
The objective was simple: build a dashboard that summarizes the
last quarter of 2024 and provides decision-makers with a quick
overview of business performance.

At this stage, everything appeared correct. The dashboard answered
the business question, the KPIs looked reasonable, and no obvious
issues were visible.

That single question changed the entire investigation.

SECTION 2

Validation Before Decision

Building a dashboard is not the end of the analysis process. Before trusting any KPI, the underlying data must first be validated.

This project intentionally simulates a real-world validation scenario. The objective was never to prove that a dashboard can be built, but to demonstrate that even a well-designed dashboard can become misleading if the data behind it is not verified first.

Instead of accepting the dashboard at face value, I went back to the source and started validating the extracted dataset before drawing any business conclusions.

The investigation began from the SQL output itself—not because the dashboard looked suspicious, but because business decisions should never rely on unvalidated data.

SECTION 3

Root Cause Analysis

The investigation traced the issue back to the SQL query that generated the dataset.

The business question was translated into SQL correctly, but one important concept was overlooked: data granularity.

The dataset mixed Order-level information with Order Item-level records.

Revenue and Quantity remained correct because both naturally exist at the Order Item level. However, counting orders directly from the joined table caused the same Order ID to appear multiple times whenever an order contained multiple products.

As a result:
  • Revenue remained correct.
  • Quantity Sold remained correct.
  • Number of Orders became inflated.
  • Average Order Value (AOV) became misleading because it was calculated using an incorrect denominator.

This was not a SQL syntax issue.
It was a modeling and business logic issue caused by using the correct query against the wrong level of detail.

The SQL engine simply executed the instructions exactly as written.

SECTION 4

Fixing the Problem

The issue could not be fixed inside Power Query because the extracted dataset no longer contained the key required to uniquely identify each order.

Without the original Order ID, removing duplicates would become guesswork rather than data validation.

The correct solution was to fix the problem at its source by rewriting the SQL query.

The query was updated to count unique orders using COUNT(DISTINCT Order_ID), preserving Order-level metrics while keeping Order Item-level measures such as Revenue and Quantity unchanged.

This ensured that every KPI was calculated at the correct level of granularity.

SECTION 5

Business Findings

After correcting the SQL query and rebuilding the dataset, the dashboard reflected the actual business performance for Q4 2024.

Key Findings

01
Total Revenue remained stable at approximately 1.45M, confirming that Revenue was never affected by the duplication.
02
The Number of Orders dropped from 274 to 215, proving that orders had previously been counted multiple times.
03
As a result, Average Order Value (AOV) increased from roughly 5.3K to 6.7K, giving a more accurate view of customer purchasing behavior.
04
Mobile Devices generated nearly half of the total revenue, followed by Office Setup, making these two categories the primary revenue drivers during the quarter.
05
Revenue declined in November, while October and December remained close to the quarterly average. This indicates a period that deserves further investigation rather than an immediate business conclusion.
SECTION 6

Beyond the Dashboard:
What This Simulation Proved

This project was never about building another dashboard.

It was designed to simulate a realistic analytical failure that can happen in real business environments, where a technically valid SQL query produces misleading business metrics because the data is aggregated at the wrong level of granularity.

The objective was to demonstrate a complete analytical workflow:

01
Start with a business question.
02
Translate it into SQL.
03
Validate the extracted data before trusting any KPI.
04
Identify the root cause instead of fixing the symptom.
05
Correct the problem at its source.
06
Rebuild the dashboard using reliable data.

This exercise reinforced an important lesson:

Validation starts long before visualization.

It begins with understanding the business question, continues through SQL design, and ends only after confirming that every reported metric truly represents the business process it is intended to measure.

More importantly, this project demonstrates not only SQL knowledge, but also analytical thinking, data validation, business understanding, and the ability to distinguish between technically correct code and business-correct results.

“

A dashboard is only as trustworthy as the logic used to build the data behind it.
